GitHub Actions Security Checklist for CI Pipelines

By Pipeline Proof Editorial · Published 2026-06-07 · Updated 2026-06-07 · 7 min read

Start by treating GitHub Actions as a release surface, not just a task runner. The checklist below focuses on permissions, pinned actions, untrusted input, secrets, and workflow dependency visibility.

Editorial note: This article is informational engineering guidance, not a substitute for a security review of a specific repository.

Key takeaways for a first workflow audit

  • Set `GITHUB_TOKEN` permissions to the minimum each workflow or job needs; GitHub documents both workflow-level and job-level `permissions` controls.2
  • Do not assume omitting `GITHUB_TOKEN` from a step fully hides it; GitHub says actions can access the token through the `github.token` context.3
  • Pin third-party actions to a full-length commit SHA when the workflow is sensitive; GitHub documents repository and organization policies for requiring full-length SHA pinning.1
  • Watch `pull_request_target` carefully: GitHub documents that this trigger receives read/write repository permission even when triggered from a public fork.2
  • Use the dependency graph and Dependabot for action visibility, but remember GitHub says Dependabot alerts for vulnerable actions do not fire for actions pinned to SHA values.1

The bottom line is least privilege plus reviewable dependencies

A practical first pass is simple: restrict the token, pin external actions, keep untrusted input out of shell scripts, and make workflow dependencies visible before they run release or deploy steps.

GitHub Actions workflows are code paths that can read repository data, call APIs, publish packages, and deploy systems. GitHub's workflow syntax lets you define `permissions` at the workflow level or inside a specific job, and GitHub states that unspecified permissions are set to `none` once any permission is specified.2

That makes a short audit worthwhile even for small repositories. A CI file that only needs to run tests can usually use read-only content access, while an issue-commenting job can grant only the issue or pull-request scopes it needs.3

A narrow permissions block beats a broad default token

Start each workflow by deciding what the job actually changes. GitHub's `GITHUB_TOKEN` guide says the `permissions` key can modify token permissions for an entire workflow or for individual jobs, and it recommends granting the least required access.3

  • Use `permissions: contents: read` for build and test jobs that only clone code.
  • Grant `issues: write` or `pull-requests: write` only to jobs that actually comment, label, or update those objects.2
  • Use `id-token: write` only for jobs that need OpenID Connect, because GitHub lists that permission as the one that fetches an OIDC token.2

Full-length SHA pinning reduces action update surprise

Third-party actions are dependencies. GitHub's secure-use reference says a full-length commit SHA is the only way to use an action as an immutable release, and it also describes repository and organization policies that require actions to be pinned to a full-length commit SHA.1

OpenSSF Scorecard treats unpinned workflow dependencies as a supply-chain risk: its `Pinned-Dependencies` check lists workflow dependency pinning by hash as a remediation for GitHub workflows used in build and release paths.4

Evidence: For sensitive release workflows, the action reference should be reviewable as a specific commit, not only as a moving tag.

Untrusted context should not flow straight into shell

GitHub's secure-use reference has a dedicated section on mitigating script injection attacks. Its recommended approaches include using an action instead of an inline script and moving untrusted values into intermediate environment variables before shell execution.1

This matters most in pull request workflows, issue-triggered workflows, and manual-dispatch workflows that turn user-controlled fields into shell commands. Treat values such as titles, branch names, labels, issue bodies, and dispatch inputs as untrusted until they are quoted, validated, or passed through a safer interface.

Secrets should move toward short-lived access where possible

GitHub's secure-use reference recommends considering OpenID Connect for workflows that deploy to cloud providers or use Vault, because OIDC can create short-lived, well-scoped access tokens for workflow runs.1

That does not remove every secret from CI, but it changes the failure mode. A long-lived cloud key sitting in repository secrets can stay valid after a bad workflow run; a short-lived OIDC-issued token is scoped to a particular run and policy.

Dependency visibility has one important SHA-pinning caveat

GitHub says the dependency graph recognizes workflow files as manifests and parses action references written as `jobs[*].steps[*].uses` or reusable workflows written as `jobs.<job_id>.uses`.1

GitHub also says Dependabot can monitor actions in workflows and create alerts when GitHub Advisory Database advisories apply, but it notes that Dependabot only creates alerts for vulnerable actions that use semantic versioning and does not create alerts for actions pinned to SHA values.1

Caution: Pinning and alerting solve different problems. Pinning reduces surprise changes; advisory monitoring helps find known vulnerable dependencies. You need both practices, plus an update process.

A short local audit catches the easy-to-miss YAML risks

Before adding a new release workflow, run a local review for broad token permissions, unpinned actions, `pull_request_target`, unsafe shell interpolation, and missing timeouts. A small workflow scanner is enough for a first pass if it reports the exact file, job, and setting to inspect.

That command is not a complete security program. It is a fast way to surface workflow patterns worth reviewing before a CI file starts publishing packages, writing comments, or deploying infrastructure.
